Audit a domain or component for anti-patterns around server state. The project convention is **Apollo Client** with the normalized cache + typed hooks generated by `graphql-codegen` (`frontend/src/shared/api/generated.ts`), NOT manual `refetch` triggers, duplicated state, or `setInterval` polling.

Arguments: `$ARGUMENTS` — path to a domain, feature directory, or feature name.

## Anti-patterns to flag

Search the target for these signals (use grep + read, don't speculate):

1. **Refresh counters / manual refetch.** State like `version`, `refreshCounter`, `reloadKey`, or calling `refetch()` from a component just to reload after a mutation. Should be `refetchQueries`/`update`/cache eviction on the mutation, or `cache.modify`.
2. **Duplicate state.** Server data copied from an Apollo query into local `useState`/context (the copy is stale by definition). Read from the query result directly.
3. **Polling via setInterval.** Use Apollo's `pollInterval` option instead.
4. **Untyped queries.** `gql` tagged queries wired by hand instead of the generated typed hooks from `@shared/api/generated`.
5. **Optimistic update without rollback.** `optimisticResponse` with a manual cache write but no error handling to revert.

## Good baseline

Read the domain `api/` re-exports of generated hooks and `frontend/src/shared/api/apollo-client.ts` (where the link chain — auth/error/logging — is declared centrally). Show contrasts against the target, not generic Apollo advice.

## Output

For each finding: **Location** (`path:LINE`), **Pattern**, **Why it's wrong** (one sentence, specific), **Recommended change** (the exact hook/cache shape that replaces it).

If nothing is found, say so in one sentence. Don't pad with generic best-practice lectures. This is an audit — surface findings, don't migrate code yourself.
